# Judge Q&A — Product Quality & Fit (25%)

## Q1: Is this actually agentic, or is it just a transcription demo with keyword rules bolted on?

It is a real agent pipeline, and the code shows the structure: `src/lib/agent.ts` builds a LangGraph `StateGraph` with three nodes — `classify_intent` → `route_to_tool` → `generate_response` — with typed state (intent, urgency, toolCalls, triageSummary) flowing between them. The agent classifies intent into four categories (triage, booking, refill, general_support), routes to a labeled tool, assigns one of four urgency tiers, and emits a structured `TriageSummary` handoff card before Sahara TTS speaks the reply. The UI surfaces the reasoning: intent and urgency badges plus deduplicated, labeled tool calls, so a judge can watch the agent's steps rather than take our word for it. That said, we are honest about the depth: this is a focused triage agent, not an open-ended planner — the graph is deliberately linear because a safety-critical intake flow should be predictable, not exploratory.

## Q2: Your production deployment has no OpenAI API key. Doesn't that mean the live product is just canned rule-based responses?

Yes, and we disclose this rather than hide it: `createLLMClient()` in `agent.ts` returns null without a key and the graph falls through to rule-based intent classification and `ruleBasedResponse()`. The important nuance is that the safety-critical behavior never depended on the LLM in the first place: `computeUrgency()` and the multilingual emergency net are deterministic on every path, so urgency tiers and emergency escalation are identical with or without a key. What degrades without the LLM is conversational quality — intent classification falls back to keyword matching and replies become canned templates instead of natural, language-mixed responses. The mitigation is architectural, not aspirational: the LLM is an enhancement layer behind a try/catch, and any OpenAI-compatible key restores full behavior with zero code changes.

## Q3: Your "tool calling" — the booking tool doesn't actually book anything. Isn't that overclaiming?

Fair criticism, and we'd answer it directly: `route_to_tool` labels and routes intents (`triage`, `booking`) and records them in the `toolCalls` state channel, but the tools do not yet execute side effects — there is no scheduling backend behind booking. What we built and validated is the agentic routing layer: intent detection, tool selection, visible tool-call traces, and a deduplication reducer, which is the part this challenge asks us to demonstrate. We deliberately did not fake a booking confirmation, because a triage product that pretends to have scheduled an appointment is a safety liability. The honest framing is: the agent decides and routes today; wiring the tools to real clinic systems is integration work, not research.

## Q4: The triage "handoff card" is just the raw transcript truncated to 300 characters, and recommended_action only ever has two values. How is that a structured clinical handoff?

The structure is real but shallow, and we know where it stops. `TriageSummary` in `agent.ts` is a typed object — symptoms, urgency (four tiers), recommended_action, and a hardcoded `not_a_diagnosis: true` flag — rendered as a distinct card in the UI. Today the symptoms field carries the transcript excerpt rather than extracted symptom entities, and recommended_action resolves to `seek_immediate_care` or `collect_more_symptoms_then_advise`. The README's mention of self-care/telehealth/in-person recommendations reflects the LLM-path response text, not the structured enum, and we should be precise about that distinction. What the card proves is the contract: a machine-readable urgency tier plus summary that a clinician dashboard could consume — the extraction depth is the next iteration, and the schema already accommodates it.

## Q5: A "handoff" implies someone receives it. With zero persistent storage and no clinic integration, the card disappears when the session ends. Who does it hand off to?

Today, it hands off to the human in the loop at the screen — the card persists in the chat UI for the patient to show a clinician or read to a provider. The absence of persistence is a deliberate privacy decision documented in `docs/ETHICS.md` (volatile memory only, nothing written to disk), and for a hackathon handling health speech we chose the safe side of that tradeoff. The cost is real: there is no queue, no EHR push, no audit trail. The design intent is that the `TriageSummary` JSON is the integration artifact — a clinic system would POST it to an intake endpoint under the clinic's own consent and retention policies, which are decisions a deployer must own, not a demo.

## Q6: The agent asks "how long have you been feeling this way?" — but the next request starts a completely fresh state. Isn't the multi-turn conversation an illusion?

In the current deployment, yes, each `/api/chat` call constructs a new `VoiceAgent` and a new state with only the latest message (`route.ts` lines 27–34) — the clarifying question is asked but the follow-up answer arrives without prior context. This is a genuine product limitation we won't dress up: the LangGraph state model supports full message history (the `messages` channel is an append reducer designed for exactly that), but we did not wire client-side history into the request before the deadline. What works today is single-turn triage with correct urgency and escalation on each utterance independently — which, not coincidentally, is how the emergency safety net should behave anyway: escalation must never depend on remembering earlier turns.

## Q7: You claim the system "responds in the language mix the patient uses," but your rule-based fallback responses are English-only strings. Doesn't the live product reply in English to a Hausa speaker?

With the LLM configured, the system prompt explicitly instructs same-language and code-switched replies, and Sahara TTS voices the response in the patient's language. Without the key, the honest answer is that `ruleBasedResponse()` returns English templates, so the fallback path does not fully honor the language-mixing claim — TTS speaks an English reply to a Yoruba patient. We partially mitigated the highest-stakes case: the emergency template is short, imperative, and paired with a red EMERGENCY badge whose meaning survives a language barrier, and the multilingual keyword net ensures the *detection* side is fully eight-language even when the *response* side is not. Localizing the fallback templates into all eight languages is a small, well-scoped fix we would ship first.

## Q8: Your emergency net covers 8 languages, but general symptom detection only covers English, Swahili, Hausa, and Yoruba. What happens to a non-emergency Igbo or Shona patient?

They fall through to `general_support` intent and low urgency unless the LLM is active — `SYMPTOM_TERMS` in `agent.ts` covers en/sw/ha/yo plus English severity phrases, and `docs/ETHICS.md` states this scope explicitly. Compounding it, our N=120 real-speech benchmark shows Sahara's ASR is weakest exactly on Igbo (0.881 WER) and Shona (0.885), so those speakers face both weaker transcription and weaker keyword coverage. Our mitigation strategy is layered: the emergency net — the case where a miss is dangerous — covers all eight languages including Igbo (`obara`, `iku ume`) and Shona (`ropa`, `kupfuma`); the benchmark publishes the per-language weakness instead of averaging it away; and the submission names Igbo/Shona as the languages where deployment needs a fallback or fine-tune first. We'd rather lose points for a disclosed gap than gain them for a hidden one.

## Q9: The emergency net is substring matching — "no chest pain" triggers emergency. Isn't that a trivially gameable safety mechanism?

It has the known failure modes of keyword matching, including the negation false positive you describe, and ASCII-folding substring match can also over-trigger on partial words. Our defense is the direction of the error: in triage, over-escalation costs a clinician a glance; under-escalation costs a patient their life. Every clinical triage protocol makes the same asymmetry explicit, and the net's output is a recommendation to seek care — never a diagnosis or a dispatched ambulance — so the blast radius of a false positive is bounded. The architecture also doesn't rely on the net alone: with the LLM active, the classifier handles semantics and negation while the net acts as an independent floor, so the two mechanisms' errors are largely uncorrelated. Improving the net (word boundaries, negation windows) is easy; we would never ship the inverse tradeoff.

## Q10: What specifically did you build for low-literacy users, beyond claiming "voice-first" in the README?

Concretely: the primary input is holding a button and speaking — no reading or typing required to report symptoms; the reply arrives as Sahara TTS audio, not just text; urgency is communicated by color-coded badges (the red emergency state reads at a glance); and the consent flow degrades gracefully — declining voice still leaves a working text interface rather than a dead end. We also engineered for the connectivity these users actually have: a 12-second TTS timeout with text-only fallback and AbortSignal timeouts mean a stalled provider queue never hangs the chat, and ETHICS.md commits to basic smartphones and low-bandwidth connections. The honest residual gap is chrome, not core: the consent modal and language selector are still text, so a fully non-literate user needs assistance for first setup — a spoken consent flow is the obvious next step.

## Q12: Walk me through how this fits a real clinic's intake workflow today — with 7.4s average latency, single-turn state, and no EHR integration, what actually works?

The realistic deployment shape today is a kiosk or intake-helper tablet: a patient speaks their complaint while waiting, and by the time they reach the desk there is an urgency badge and a summary card the nurse reads in seconds — the card standardizes the first question every intake asks anyway. Latency supports this: 7.4 s/utterance mean on the N=120 run is acceptable for a triage exchange (patients pause longer between sentences in person), and the emergency path does not wait on anything — the keyword net fires deterministically on the transcript. What does not exist yet — multi-turn memory, EHR write-back, a triage queue — is exactly the set of things that require a clinic partner's data governance decisions, which is why we built the integration contract (the `TriageSummary` JSON and the `/api/chat` response shape) rather than a pretend integration. The product claim we stand behind is narrow: it makes the symptom survive transcription and arrive prioritized, in the language the patient actually spoke.
